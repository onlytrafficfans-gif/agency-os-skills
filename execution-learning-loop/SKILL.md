# Execution Learning Loop

Improve decisions from observed outcomes, not from adding tools for their own sake. A skill changes instructions; it does not retrain the model, guarantee future invocation, grant access, or prove improved performance.

## Diagnose before adding
Inspect a small relevant sample of current artifacts, failed attempts, or user-provided history. Record the objective, actual result, evidence, time lost if known, and next unresolved dependency. Separate tool/access failure, unclear decision, implementation defect, lack of buyer evidence, and unnecessary scope. Do not blame missing tools when a decision or distribution is the bottleneck.

Search existing local skill names and descriptions before creating another. Read likely matches and verify their referenced files, tools, paths, and platform assumptions. Installed instructions may target another harness or contain stale examples. Treat those as references requiring adaptation, not commands to execute blindly. Do not remove existing skills or alter user configuration without scoped authorization.

## Make one useful correction
Choose the smallest patch supported by the failure: a clearer completion criterion, a reusable artifact, a tool fallback, a narrower experiment, or a corrected skill. Preserve task scope and existing approvals. Prefer measured effort and observed cost over arbitrary model routing or unverified claims of savings.

Before writing an executable helper, identify repeated use and why deterministic automation improves reliability. For skills, keep triggers narrow and avoid global rules that interfere with unrelated creative or engineering work. Follow the skill-creator workflow where available.

## Evaluate behavior
Choose realistic cases with expected observable outcomes, including one counterexample that should not activate the skill. Include a misleading-success case where appropriate: a test payment, stale snapshot, simulated customer, or green build. Check whether the workflow reaches the right decision and respects scope. Syntax validation alone is not behavioral validation.

If independent delegation is authorized and worthwhile, evaluate with a neutral task and minimal artifacts. Otherwise do a transparent local scenario review and label it as such. Do not call a self-review independent or claim measured improvement without a comparable before/after task.

Keep a short project-local decision record: observation, correction, evidence, result, and unresolved issue. Update personal/global memory only when the user explicitly asks. Do not schedule background learning, install remote code, contact people, or mutate live services as an implied part of self-improvement.

End with the correction actually installed, how it was checked, where it applies, and what remains unknown. Stop expanding the system once the demonstrated gap is covered.

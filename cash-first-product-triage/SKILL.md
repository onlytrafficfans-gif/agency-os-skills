# Cash First Product Triage

Start with the actual product and buyer evidence. Do not price from an idea, screenshot, project name, or old memory.

## Establish reality
Confirm the requested repository, branch, running environment, and relevant flows before making claims. Inspect the user journey and implementation for working capabilities, demos, dependencies, delivery effort, and payment/access boundaries. Mark each important fact observed, reported, inferred, or unknown, with its source and date. Historical evidence does not establish current state.

Identify the intended buyer, costly recurring problem, existing workaround, reachable acquisition channel, and reason to buy now. If buyer access is unknown, make that uncertainty visible rather than assuming traffic will arrive.

## Make the decision
For portfolio requests, compare only the candidates in scope using evidence for buyer access, demonstrated pain, time to deliver, marginal cost, support burden, and time to collect payment. Use qualitative confidence rather than invented numerical probabilities. Prefer one active commercial experiment unless the user chooses otherwise. Preserve other projects and the user's selected product direction.

For an app, compare self-serve purchase, a tightly scoped paid pilot, and a productized deliverable only where the existing capability supports them. Manual delivery is acceptable when disclosed and repeatable. Never describe manual service as autonomous software. Do not redirect a requested build into consulting without the user's agreement.

Price is a testable hypothesis until buyers accept it. State included outcome, exclusions, delivery time, acceptance criteria, price basis, costs, and payment timing. Inspect current official competitor pricing only when it helps the decision; competitor pricing alone does not prove willingness to pay.

## Produce an executable handoff
Deliver one recommended offer and the evidence against it; the smallest experiment that can disprove demand; one concrete local buyer-facing artifact; the next task and owner; and the exact dependency that prevents collecting payment. Prefer existing payment tooling and a narrow repair over a new billing system.

Separate gross collected payments, refunds, net collected cash, fees, variable costs, and owner labor. Report profit only with its definition and known costs. Never substitute pipeline, checkout creation, test payments, or an unsigned proposal for revenue.

Use existing research, outreach, and implementation skills where needed. Creating an offer does not authorize sending messages, publishing, spending, changing live prices, or charging anyone. Honor established scoped authorization without asking twice.
